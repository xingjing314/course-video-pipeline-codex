## 三、七步流程

### 第 1 步｜输入：定稿口播稿

`第七章-L01完整口播稿V0.1.md`（73 行 / 2145 字，去标点）。**全程未改一个字**；后面所有时间、字幕、cue 都以它为准。

### 第 2 步｜设计：分镜方案

`第七章-L01-画面分镜方案V0.1.md`（396 行）：31 个镜头、8 个叙事段、10 件视觉资产（A1–A10）、每镜的画面/动效/声音/意图，以及口播逐行覆盖核对表。

这一阶段只产出**文档**，没有代码。它是后续所有实现的唯一依据。

### 第 3 步｜资产：10 件视觉资产逐个做原型

| 资产 | 形态 | 评审产物 |
| :--- | :--- | :--- |
| A1 考情卡 / A2 时间轴 / A3 四笔账 / A4 三件事 | 静态卡 | `out/a14/*.png` |
| A5 四关轨道 | 状态机 0–6 | `out/a5/*.png` + mp4 |
| A6 刻度尺 | 并入 A8 | — |
| A7 真题卡 | 模板升级（cue 驱动） | `out/a7/*.png` + mp4 |
| A8 身份证卡 | 状态机 0–2（累积式） | `out/a8/*.png` + mp4 |
| A9 口诀卡 | 5 阶段 | `out/a9/*.png` + mp4 |
| A10 同源小卡 | 并入 A7 | — |

每件都单独出一个 Lab composition（`A5GateTrack` / `A7ExamQuiz` / `A8IdCard` / `A9Mnemonic` / `A14Cards`），只在 Lab 层挂 `TechNetwork` 背景，资产组件本身透明——这样将来换背景不用动资产。

### 第 4 步｜接入：契约 + 路由

新增 7 个 visualType（判别联合 12 → **19 类**）：

| visualType | payload | 用途 |
| :--- | :--- | :--- |
| `exam-stats` | 数据块 + 标签 + 脚注 | A1 |
| `chapter-timeline` | before/after + 追问 | A2 |
| `four-accounts` | 固定 4 格 + 印章 | A3 |
| `three-steps` | 2–4 步 + 交付物 | A4 |
| `gate-track` | `{ stage 0–6, beatFrames? }` | A5 |
| `id-card` | `{ stage 0–2 }` | A8 |
| `mnemonic-card` | `{ stage 0–4, cuts? }` | A9 |

三处改动：`contracts/visual-props.schema.ts` 加 schema；`prototypes/scene-adapters.tsx` 把状态机组包装成"吃 payload 的场景组件"；`SceneRouter` 加 case（`default` 的 `never` 穷尽检查自动兜底）。

验证用冒烟测试 `A14Smoke` / `A59Smoke`：**payload 先过 `CompiledSceneSchema.parse()` 再路由**，确保契约、联合、分发三层都通。

### 第 5 步｜拼片：S01–S31 成片时间线

`L01Film.tsx`：31 镜按真实码拼成一条序列，17 个渲染段（跨镜资产合并成一段，例如 A5 跨 S08–S13）。

分段的理由：A5/A7/A8 是**跨镜头**的，按"一镜一段"切会丢掉状态连续性。段内多状态由 `cuts` 表驱动——落到第几段就是第几个状态。

拼片时发现 **31 镜里有 5 镜没有资产**（S01 标题、S03 学法、S04 章节定位、S26 同源小卡、S28 命题套路），当轮补齐，否则时间线是空的。

### 第 6 步｜配音：IR 桥 → TTS → 对齐

原来的卡点：`npm run compile` 的入口是《合一稿》Markdown 表格，而 deepseek 版只有口播稿 + 分镜方案，**没有可喂给 TTS 的输入**。补了两个脚本：

```bash
node --experimental-strip-types scripts/build-l01-ir.ts      # 口播稿 + 覆盖表 → StoryboardIR（31 场景）
node --experimental-strip-types scripts/run-l01-audio.ts --mode=cuda   # TTS + 强制对齐
```

产出落在 `workspaces/ch07-L01-ds/`：逐场景 wav、`ch07-L01-ds-full.wav`、`audio-timeline.json`、`aligned-tokens.json`、`.srt`。

`--mode=synthetic` 可以无 GPU 走一遍链路（静音 WAV + 均匀字级 token），用于验证管道，不用于交付。

### 第 7 步｜重算：音频为准

配音一落地，分镜估算的 507 s 作废：

```bash
node --experimental-strip-types scripts/build-l01-timeline.ts
```

从 `audio-timeline.json` 派生：镜头起止（`l01-generated.ts`）、字幕（`l01-captions.json`）、以及所有 cue——不再手填，改为在 token 流里搜短语定位（"干扰项""选C""A 选项说""第一步…第四步"）。

| 项 | 分镜估算 | 配音实测 |
| :--- | ---: | ---: |
| 总长 | 507 s | **591.1 s（+16.6%）** |
| 帧数 | 15210 | **17734** |
| S09 四阶段 | 27 s | **39 s** |

### 第 8 步｜出片：四件套

```bash
# 有声 + 字幕
node_modules/.bin/remotion render src/visual/index.ts L01Film \
  deliverables/ch07-L01-ds/ch07-L01-ds-voiced-captioned.mp4 \
  --gl=angle --hardware-acceleration=if-possible --concurrency=8

# 无声 + 无字幕
node_modules/.bin/remotion render src/visual/index.ts L01FilmSilent \
  deliverables/ch07-L01-ds/ch07-L01-ds-silent-clean.mp4 \
  --gl=angle --hardware-acceleration=if-possible --concurrency=8
```

两个 composition 与 `L01Film` 同一个组件，只靠 `includeAudio` / `includeCaptions` 两个 props 区分。

SRT 与 WAV 直接从 `workspaces/ch07-L01-ds/` 拷入 `deliverables/`，无需转码。

| # | 现象 | 根因 | 修法 |

| 1 | 时长估短 16.6% | 按 4.3 字/秒估算，实际约 3.6 字/秒 | 改为音频驱动；分镜时间码只作制作参考 |

## 六、复现清单

从零到四件套，按顺序：

1. 定稿口播稿（人工） → 2. 写分镜方案（人工） → 3. 逐件做资产原型并在 Studio 里评审
4. `build-l01-ir.ts` 生成 IR → 5. `run-l01-audio.ts --mode=cuda` 出配音
6. `build-l01-timeline.ts` 用音频重算时间线与 cue → 7. `rebuild-l01-captions.ts` 重切字幕（可选）
8. `L01Film` / `L01FilmSilent` 两次渲染 → 9. 拷 SRT 与 WAV 进 `deliverables/`
10. 核验：有声版 `h264+aac`、静音版仅 `h264`，两者帧数均为 17734，SRT 末条时间 ≤ 片长

## 七、已知限制

1. **A5 的连续性只在成片层成立**。走 `SceneRouter` 时是一镜一场景，入场动效会重放；要不要为通用性放弃连续性，是内容取舍，尚未定。
2. **IR 里仍有 15 镜是 `title-card` 占位**（S01/S03/S04、三道真题、S26/S28）。音频阶段不读视觉字段，所以不影响配音；但要走 `compile` 全链路就得补齐。
3. **字幕切分是启发式**：以标点优先、字数兜底，没有做"语义完整"判断。单句过长时仍可能切在语义中途。
4. **渲染耗时**：GPU 2–3 分钟/条，CPU 约 30 分钟/条，相差一个数量级——这不是优化问题，是设备可见性问题。

## 八、最重要的一条教训：顺序纪律

### 规则

**先定口播，再由口播定音频，最后由音频定时间线与字幕。** 上游只要还可能变，下游就不许焊死。

### 代价（507 s → 591 s）

分镜阶段按 4.3 字/秒估算全片 507 s，据此写死了 31 镜的起止、cue 帧、字幕行。真实配音出来是 **591.1 s（+16.6%）**，等于默认语速算快了 16%。于是下面这些全部返工：

| 返工对象 | 原值 | 重算后 |
| :--- | ---: | ---: |
| 总帧数 | 15210 | 17734 |
| 镜头起止（31 处） | 手写表 | 由 `audio-timeline.json` 派生 |
| 真题 cue（9 个） | 手填帧号 | 在 token 流里搜短语定位 |
| A5 四门节拍 | 48 帧/门 | 268 帧/门 |
| 字幕 | 99 条推算 | 143 条 token 派生 |

一轮返工的代价不只是时间，而是**中间产出的全部作废**——那版 507 s 的成片、那版字幕、那版 cue，一个都用不上。

### 为什么会犯

因为"估算"看起来便宜：4.3 字/秒一乘就有时间轴，不用等配音、不用等对齐，当天就能出片。**它确实更快，只是快在了错误的地方**——它让下游提前开工，代价是下游全部重做。

真正的判据不是"能不能算出来"，而是：**上游还会不会变？** 会变，就不要把下游焊死。

### 怎么执行

三个检查点，每个都要求"以实测为准"：

1. **时间码**：分镜里的秒数只是制作参考，标注清楚"非交付标准"；任何写死帧号的代码都要能一键重算。
2. **时间线**：以 `audio-timeline.json` 为唯一真源，镜头表、cue、字幕全部从它派生（`build-l01-timeline.ts` 就是干这个的）。
3. **字幕**：以 token 的时间为准，不以字数比例估算。

外加一条工程约束：**派生脚本必须幂等**——重录一次，跑一条命令就全部刷新，不靠人手改任何一个数字。本次的 `build-l01-timeline.ts` 满足这一条，所以第二次重算只花了十几秒。

### 适用范围

不止这一支片。任何"稿 → 音 → 画"的内容生产都适用：**声音是时间的母版，画面跟着声音走**。反过来（先排画面、再配音去凑）只在一种情况下成立——画面本身有刚性时长约束（比如必须卡某个音乐节拍），而教学视频不属于这一类。
