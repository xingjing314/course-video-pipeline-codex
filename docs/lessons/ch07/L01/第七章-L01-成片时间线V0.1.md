## 五、字幕轨（已挂）

`CaptionsOverlay` 已挂在片尾，数据来自 `src/visual/prototypes/l01-captions.json`（99 条），由脚本从**口播稿 + 分镜时间线**生成：

```bash
node --experimental-strip-types scripts/build-l01-captions.ts [口播稿路径]
```

规则：

1. 口播稿的 50 个自然段，按 `PARAGRAPH_SHOTS` 落到所属镜号（这张表就是分镜第七节的覆盖核对表）；
2. 同一镜内的多段，按**字数比例**瓜分该镜时长；
3. 段内按标点切成 ≤ 38 字的字幕行，再按字数分时间；
4. 同时导出 `out/l01/l01-film.srt`，供后续配音/校对直接用。

**这不是配音对齐的结果。** 现在的字幕时间是"按分镜节奏推的"，等 TTS 与字级强制对齐就位，`cue-point-resolver` 会用真实词级时间替换这张表——到那时 JSON 改由流水线产出，脚本退役。

顺带修了一个真问题：A5 的"四门点亮"原本用评审片的 48 帧节奏，放进 27 秒的 S09 里，四门 9.6 秒就全亮完了，字幕才念到第二步。现在 `GateTrack` 暴露 `beatFrames`，成片里按 S09 的 810 帧除以 4 给到 180 帧/门。

## 六、配音入口（IR 已生成）

配音原来卡在一个缺失的输入上：`npm run compile` 的入口是《合一稿》Markdown 表格，而 deepseek 版只有口播稿 + 分镜方案，没有那张表。现在补了一条桥：

- **IR 的视觉字段是占位**：只有 S02/S05/S06/S07 挂了真实的卡（`exam-stats` / `chapter-timeline` / `four-accounts` / `three-steps`），其余 27 镜统一 `title-card`。音频阶段只读 `sceneId / clauses / pauseDirectives / narration / narrationSha256`，**占位不影响配音**。
- **synthetic 已验证链路可用**：0.1 s 跑完 31 场景，出 545.4 s 的静音 WAV + 151 条字级 token 字幕。

### 一个必须先想清楚的后果

**真实配音会重新定片长。** synthetic 用"字符数 × 220ms"估算，得到 545 s；真实 TTS 会得到第三个数字。现在的 507 s 是分镜估算——一旦音频落地，镜头的 `from/to`、字幕、cue 全部要按音频重算，`l01-timeline.ts` 那张表就作废（改为从 `audio-timeline.json` 累积生成）。

## 七之二、字幕断句返工（已完成）

原来的 `buildCaptionsFromTokens` 只按"停顿 ≥180ms 或满 16 字"切，必然切出"…三个身份信"这种半句。

排查时发现一个更麻烦的事实：**对齐 token 不是逐字的**——数字会被合并成一个块（`2.68%，2026` 变成单 token `2682026`），标点与破折号被整体丢弃。所以"按字符逐一对齐"这条路本身是错的。

改成**按 clause 对齐**：

1. 原文按标点切成 clause（保留标点）；
2. 每个 clause 归一化后，在 token 流拼成的字符串里**顺序查找**，命中段落的首末 token 即该 clause 的时间；
3. 合并 clause 成行：句末标点且 ≥4 字就断、逗号类 ≥10 字再断、≥26 字强制断；
4. 单行仍 >28 字的，按「：；，、」优先级二次切分，时间按字数比例拆。

结果对比：

| 指标 | 旧 | 新 |
| :--- | ---: | ---: |
| 条数 | 209 | **139** |
| 平均可见字数 | 8.6 | **16.6** |
| 以标点结尾 | — | **90%** |
| 最长 | 24（硬切半句） | 34（单 clause 无法再切） |

改动落了三处：`srt-exporter.ts` 新增 `buildCaptionsFromNarration`（保留旧函数不删）、`audio-runner.ts` 两处调用切到新函数（以后跑 L02/L03 直接受益）、`scripts/rebuild-l01-captions.ts` 用现有 token 重切并回写 `audio-timeline.json`、`.srt` 与成片字幕。

实现分三层：

2. `prototypes/scene-adapters.tsx`：把"状态机组件"包成"吃 payload 的场景组件"，用场景本地帧驱动入场；
3. `SceneRouter` 三个 case；`default` 的 `never` 穷尽检查自动兜底。

冒烟测试 `A59Smoke`：四个场景（stage 4 / stage 2 / stage 4 / stage 6）**先过 `CompiledSceneSchema.parse()` 再路由**，出图在 `out/a59/`。

### 一个必须承认的语义差异

流水线是"**一个镜头 = 一个场景**"，而 A5/A8/A9 原本是**跨镜头累计**的。接进路由后，每个镜头是一次硬切，入场动效会重放——不再有"同一张图连续演进"的丝滑。

所以现在有两条路并存：

- **成片层**（`L01Film`）继续让 A5 跨 S08–S13 连续演进，这是分镜设计的初衷；
- **流水线层**（`SceneRouter`）按镜头切，牺牲连续性换取"IR → 场景"的通用性。

真要走 `compile` 全链路，就得统一到后者；是否放弃连续性，是内容层面的取舍，不是技术问题。

## 六、验收方式

> **渲染分工（2026-10-24 定）**：成片渲染一律交给用户本地 GPU（RTX 5060 Ti）执行，通常 2–3 分钟。
> Agent 侧沙箱没有 `/dev/dri` 与 nvidia 设备节点，只能 CPU 光栅化（约 30 分钟/条），
> 因此只用于**小片段验证**（≤60 帧的 probe、或单帧 still），不再跑全片。

```bash
cd /projects/gaoxiang/course-video-pipeline-Gemini
npm run studio                       # 选 L01Film，拖时间轴逐镜检查
node_modules/.bin/remotion render src/visual/index.ts L01Film out/l01/l01-film.mp4 \
  --browser-executable=/opt/google/chrome/chrome
```
